Comment peut-on évaluer la qualité d'exécution d'une tâche complexe par un [[agent]] ? 

Ce qui m'intéresse ici tient à l'image d'une tache complexe, bien réalisée, la réalité sur laquelle l'[[agent]] va s'appuyer pour s'améliorer. Se rend-on suffisamment compte du fait que cette image détermine presque l'intégralité du travail qui sera effectué à l'avenir ? Puisqu'on ne sait plus trop bien ce que les agents ne sont pas capables de faire (🙃), il ne nous reste plus qu'un choix : celui de l'image contre laquelle l'[[agent]] viendra s'appuyer pour apprendre à effectuer une tache.

Cette réflexion rejoint celle de la manière dont on créé les spécifications qui vont guider l'[[agent]], celles que l'on les trouve généralement normalisées dans les benchmark d'évaluation. Mais comment fonctionnent-ils sur des taches réelles complexes ?

Merril et al. (2026) ont crée [[Terminal]]-Bench 2.0, un benchmark pour évaluer la capacité des agents à opérer des tâches "inspirées des problèmes rencontrées dans des flux de travail réel". On y trouve pour chaque tâche "un environnement unique, **une solution, rédigé par un humain** et une batterie complète de [[test]]s de vérification"

Prenons un exemple concret. La tâche dite "[[Hugging Face]] [[Model]] [[inference]]" ([ici](https://hub.harborframework.com/tasks/terminal-bench/hf-model-inference)). C'est une tâche qu'un [[data scientist]] peut effectuer pour réaliser une analyse de sentiments à partir de texte écrit. Dans le benchmark, cette tâche est décrite comme une suite de quatre étapes : 
1. Télécharger un modèle depuis [[Hugging Face]]
2. Créer une API pour accéder au modèle
3. Faire tourner le service d'analyse sur l'ordinateur
4. Garder ce service actif dans l'arrière-plan de l'ordinateur


Comme il s'agit d'une tâche informatique, l'image ici de la tâche bien réalisé est du code informatique, à savoir : 

```shell
# Create directory for model cache
mkdir -p model_cache

# Download and save the model and tokenizer
python3 -c "
from transformers import AutoModelForSequenceClassification, AutoTokenizer

# Download and save the model and tokenizer
model_name = 'distilbert-base-uncased-finetuned-sst-2-english'
model = AutoModelForSequenceClassification.from_pretrained(model_name)
tokenizer = AutoTokenizer.from_pretrained(model_name)

etc.

```


Mais la véritable question que je me pose maintenant, c'est de savoir comment est-ce que l'on peut mesurer l'écart entre cette vision parfaite de l'exécution d'une tâche et l'exécution réelle de cette tâche par un [[agent]] quelconque ? C'est ici qu'intervient toute l'ingénierie qui va généralement de pair avec un benchmark d'évaluation. 

Si je reprends l'exemple de [[Terminal]]-Bench 2.0, il va de pair avec un [[agent harness]] dit [harbor](https://www.harborframework.com/)

# Fonctionnement d'harbor : [[agent harness]] d'[[evaluation]] 

En premier lieu, harbor crée un environnement isolé dans lequel l’[[agent]] va effectuer sa tâche. Cette étape est essentielle pour éviter que l’évaluation soit polluée par des éléments parasites de l’environnement.   

Dans cet environnement, l’[[agent]] se voit adjoint un modèle de langage et un certain nombre d’outils pour qu’il effectue la tâche. 

Il est amusant ici de noter qu’il ne faut surtout pas placer dans cet environnement isolé les tests qui serviront à évaluer les résultats de l’[[agent]], au risque que l’[[agent]] les découvre et « triche ». Comme un enfant qui découvrirait les consignes d’évaluation avant un contrôle. 

Les tests sont donc injectés après le travail de l’[[agent]] et appliqués. Dans la tâche qui nous sert d’exemple, les tests consistent à regarder : 
  
1. Si l’[[agent]] a bien téléchargé le modèle 
2. Si le modèle retourne bien une vraie analyse de sentiment 
3. Si le service qui retourne l’analyse sait bien gérer les erreurs 

**Donc, d’une certaine manière, les tests récupèrent des preuves irréfutables que l’[[agent]] a bien effectué son travail**. Si les preuves existent, alors on considère que l’[[agent]] a réussi sa tâche, sinon, c’est qu’il a échoué. 
  
La réussite ou l’échec se traduit dans un score allant de 0 à 1, qui devient alors une « récompense ». C’est à dire que le résultat du travail de l’[[agent]] est ici toujours considéré comme un indice qui pourra orienter un entraînement futur de celui-ci. Par entraînement j’entends ici : l’adjonction de meilleurs outils ou l’amélioration des [[skills]]. 

Voilà pour une synthèse brève sur le fonctionnement des outils d'évaluation des agents. Maintenant, qu’à-t-on appris ici sur l’image de ce que constitue une « tâche bien réalisée » ? 

Qu’elle se traduit par un certain nombre de preuves qui sont censées témoigner de sa bonne réalisation. Ce qui est pose question ici : toutes les tâches produisent-elles des preuves irréfutables de leur bonne réalisation ? 

Pour une tâche qui consiste à produire du code, on répondra par la positive mais pour d’autres tâches moins déterministes, peut-on seulement écrire ces preuves ? J'ai regardé alors une autre tâche présente dans un autre benchmark d'évaluation, le [Legal Agent Benchmark](https://github.com/harveyai/harvey-labs) (LAB), créé par Harvey. Une tâche est décrite très simplement, d'une phrase, à laquelle est adjointe une vingtaine de documents : 

> Review the attached SEC examination documents and draft a privileged audit findings memorandum for the board meeting.

Dans ce benchmark, il n'existe pas d'image de la tâche bien réalisée, seulement des critères d'évaluation laissées à la main d'un [[LLM-as-a-judge]] : 

```toml
[judge]
judge = "anthropic/claude-sonnet-4-6"
mode = "individual"

[scoring]
aggregation = "all_pass"

[[criterion]]
name = "c-001"
description = """Identifies IPO allocation favoritism toward higher-fee funds

PASS if the memorandum identifies that Whitestone disproportionately allocated IPO and secondary offering opportunities to the Flagship Fund and Capital Partners Fund, which pay the highest fees. Must reference the pattern (e.g., Flagship received 68 of 73 opportunities or 93.2%, while Credit Dislocation received only 11 of 73 or 15.1%). FAIL if the allocation favoritism finding is missing or described only in vague terms without identifying the fee-driven motivation."""
type = "binary"
files = ["/workspace/output/audit-findings-memorandum.docx"]

[[criterion]]
name = "c-002"

etc.

```

Le juge va ici récupérer l'[[output]] de l'[[agent]] et regarder si un certain nombre d'éléments sont présents. En fonction, il décide si oui ou non la tâche a réussi.
